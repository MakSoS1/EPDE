# НИР-1 — оптимизация E1 без изменения постановки

**Статус:** инженерная реализация опубликована в ветке `nir1`; численные тесты и измерения на GitHub VM являются обязательной проверкой, не предполагаемым результатом. **Исходный EPDE по умолчанию не изменён.**

## Область работ

Точный E1 — разрешённое ускорение, сохраняющее выборку, библиотеку, бюджет эволюции, метрику и математическую процедуру оценивания. Сокращение поколений, подбор меньшего подмножества точек, подмена точной проверки быстрым surrogate или снижение численной точности относятся к **E2-приближениям** и не активированы.

### E1-A: один проход для Gram в метрике нестабильности

Функция `_het_components` уже вычисляла блочные достаточные статистики. Первоначальный `nir1_excess_scores` дополнительно выполнял `A.T @ (W @ A)`, повторно читая весь набор наблюдений. Теперь нормальная матрица собирается из уже посчитанных блоков:

\[
G_{SS}=\sum_{b=1}^{B}G^{(b)}_{SS}.
\]

Весовая схема и свободный член остаются неизменны. При плохо обусловленной Gram-матрице (оценка `cond(G)>1e8`, либо нечисловой результат) используется исходное прямое умножение, и fallback фиксируется счётчиком `nir1.precision_direct_gram_fallback`. Округления при суммировании по блокам могут различаться; именно поэтому обязательны допуски и end-to-end проверки.

### E1-B: одни блочные Gram-матрицы на все шаги RFE

При `nir1_excess` или `nir1_protected` RFE вычисляет полную систему блочных Gram-матриц **один раз на вызов `PhysicsInformedLasso.fit`**. Для каждого удалённого токена берётся соответствующая подматрица. Распределение на временные блоки сверяется с оригинальным расчётом, при несовпадении используется прежний путь, а fallback виден по счётчику `nir1.block_gram_partition_fallback`. Сложность проходов по `n` наблюдениям уменьшается с повторяемой на каждой итерации до одной предварительной свёртки; численное решение в пространстве коэффициентов остаётся прежним.

Для прямой контрольной пары:

```bash
NIR1_DISABLE_GRAM_CACHE=1 python -m projects.nir1_stability.nir1.cli epde \
  --dataset ode --variant nir1_protected_regulator --seed 0 --data-seed 0 --output /tmp/nir1-reference.json
NIR1_DISABLE_GRAM_CACHE=0 python -m projects.nir1_stability.nir1.cli epde \
  --dataset ode --variant nir1_protected_regulator --seed 0 --data-seed 0 --output /tmp/nir1-cached.json
python -m projects.nir1_stability.nir1.compare_full_e1 \
  --reference /tmp/nir1-reference.json --cached /tmp/nir1-cached.json --output /tmp/nir1-parity.json
```

Нужно различать **совпадение значений критерия на заданном support** и **совпадение полного эволюционного поиска**, чувствительного к малым различиям. Второе проверяется отдельным workflow на `ode` и `burgers` при неизменном бюджете 16×5. При расхождении структур E1-B считается НЕ прошедшим регрессионную проверку и не допускается к научному сравнению как точное ускорение.

### E1-C: не повторять эволюцию для сравнения двух селекторов

Исходный EPDE `default` и `nir1_sparsefront` используют одинаковую библиотеку, фитнес, регуляризацию и эволюционную конфигурацию; различается только финальный выбор на готовом фронте. Поэтому метод `paired_replay.py` применяет два селектора к **одному и тому же сохранённому фронту**. Экономится целый второй поиск; при этом сравнение становится строже, потому что кандидаты гарантированно одинаковы.

```bash
python -m projects.nir1_stability.nir1.paired_replay \
  --input /tmp/epde-default.json --truth-dataset ode --output /tmp/paired-selector.json
```

Результат имеет явный тип `PAIRED_POSTPROCESSOR_NO_NEW_EPDE_RUN` и `source_front_sha256`. Его нельзя выдавать за независимые два вычислительных прогона. **Для новой регуляризации или изменённого критерия этот способ недопустим:** они способны изменить сам фронт.

## Автоматические проверки

1. `.github/workflows/nir1-perf.yml` — точная паритетность score на обычных/взвешенных/почти вырожденных матрицах плюс 4 измерения времени метрик и RFE до/после с сохранением JSON и исходного SHA.
2. `.github/workflows/nir1-full-e1-parity.yml` — настоящий `EPDE 16×5` с включённым/выключенным кэшем, сохранение двух сырых JSON, сравнение Pareto-структуры, выбранного закона и метрик на `ode` и `burgers`.
3. `projects/nir1_stability/tests/test_exact_gram_reuse.py`, `test_paired_replay.py` — непрерывная регрессия математической эквивалентности и отсутствия утечки oracle.
4. Ранее уже существующий `nir1-smoke.yml` проверяет общий контракт EPDE и PIC.

## Как измерять реальное улучшение

**Целевые пороги (не измеренные результаты):**
- Для `E1-B`: медианное ускорение по серии RFE support ≥ **1,5×**, одновременно с проверкой точного восстановления коэффициентов/выбора support и контролем деградации в плохой обусловленности.
- Для **полного EPDE**: целевое ускорение ≥ **1,2×** по парным задачам и seed, без снижения частоты точного восстановления; минимум два разных семейства систем в пилоте и более широкое подтверждение до статьи.
- Для **качества алгоритма**: увеличение `success_selected` ≥ **10 процентных пунктов** на независимых задачах; отсутствие выборочной отчётности и скрытого сокращения бюджета.
- Даже при выигрышном S1b/S1c нельзя заявлять переносимость S3 до подтверждения на отдельном наборе систем/начальных условий.

**Публикация показателей:** после завершения GitHub Actions только из реально созданных `e1-*.json` и `e1-full-parity.json`, с полным commit SHA и условиями запуска. Единственный быстрый случайный прогон не даёт устойчивую оценку wall-clock. Провалы тестов не исключаются.

Нельзя считать это новым ускорением НИР-1 или повторно переписывать уже оптимизированный код без нового профиля.
