# НИР-1 — протокол S2/S3, без преждевременного запуска

**Дата:** 10.10.2026. **Статус:** план подтверждения, НЕ результаты. **Исходная ветка:** `nir1`. На момент фиксации S1 GitHub Actions #38076377893 ещё выполняется.

## 1. Научная граница между этапами

- **S0:** проверка отдельно взятых регрессий и критериев на фиксированных синтетических матрицах.
- **S1:** разведочная 2×2 абляция в настоящем EPDE, шесть систем, пять сидов, четыре варианта.
- **S2:** подтверждение заранее выбранного *одного* лучшего варианта против неизменённого baseline на иных системах. Если S1 не выявил ни одного приемлемого варианта, **не объявлять победителя**; S2 становится исследованием границ применимости с фиксированной отрицательной гипотезой.
- **S3:** проверка переносимости на действительно новые начальные условия, более сложные режимы динамики и отдельные семейства PDE. Настройки замораживаются до раскрытия S3.

## 2. Входной барьер

Прежде чем выделять вычислительный бюджет S2, вручную и скриптом проверить:

1. S1 запущен с неизменённого SHA `8d3aa947bc074000dee6d8acf96c4862eb74d81c`; сравнения не берут файлы из разных коммитов.
2. Замороженный `planned.json` содержит 120 уникальных заданий; его `manifest_sha` совпадает с опубликованным при запуске.
3. Для каждого ID имеется один окончательный согласованный статус; повреждённые и противоречивые файлы обнаружены, не замолчаны.
4. Статистика не использует истины для выбора гиперпараметров и не использует повторные сиды как независимые физические системы.
5. Записать `SHA256` полного `S1_SUMMARY.json`, дату решения, зафиксированный алгоритм, его гиперпараметры, список S2-систем, список S3-систем, бюджет вычислений и метрики в отдельный неизменяемый `confirmation_decision.json`.
6. До решения S1 ни один YAML S2/S3 нельзя перемещать в `manifests/launch`. Настоящая команда `cli plan` уже требует `frozen_confirmation_sha` для S2/S3; этого поля недостаточно как научного доказательства, поэтому решение обязательно проверяется дополнительно по S1-артефакту.

## 3. Набор независимых задач и статистическая мощность

`configs/splits.yaml` в текущей версии содержит:
- development: `ode, vdp, duffing, lv, lorenz, ac, burgers`;
- validation: `burgers_inviscid, kdv, kdv_cossin`;
- heldout: `wave, ks, pde_compound, pde_divide, ns`.

В **S1 уже присутствуют** `ode, vdp, duffing, lv, ac, burgers`; они не подходят для независимого S2. Валидация содержит всего **три** задачи. Все восемь задач validation + heldout нельзя использовать для подбора и одновременно называть S3 независимым. Необходимо либо увеличить банк независимых, реально поддерживаемых задач, либо честно ограничить статистическую значимость и не заявлять универсальную переносимость.

Для двустороннего точного sign-flip теста минимальный p при `G` независимых системах равен `2 / 2^G` при одинаково направленных эффектах. При `G=5` минимум `0.0625`; при `G=6` — `0.03125`, который после трёх сравнений Холма не достигает `0.05`. При заранее определённом **одном** сравнении в S2 семь независимых систем могут дать минимум `0.015625`; однако этого всё равно недостаточно для доказательства универсального превосходства и необходимо учитывать доверительный интервал.

S2 рекомендуется: не менее **семи действительно независимых систем, не использованных при подборе**, минимум 20 парных сидов на систему только для оценки стохастичности оптимизатора. Сиды **не повышают** число независимых физических систем. До добавления поддерживаемых задач и фиксации списка выпуск S2 считается заблокированным.

## 4. Первичная и вторичная метрики

- **Первичная:** доля точного восстановления *выбранного* уравнения среди всех запланированных поисков; алгоритмические `crash/timeout` — неуспех, незавершённый инфраструктурный запуск — блокировка анализа.
- **Вторичные:** истинная структура на фронте Парето; ошибки включения и удаления, ошибка коэффициентов только для корректно сопоставленных структур, время полного поиска и peak RAM, ошибочный выбор при наличии истины на фронте.
- Пары строятся по `system + data_seed + optimizer_seed`. Отсутствие любой стороны пары блокирует подтверждающее сравнение.
- Кластерный bootstrap и парный sign-flip выполняются по **целым системам**, а не отдельным сидами.
- Критерий решения: направление эффекта и научно существенный размер улучшения заранее фиксируются; p-value сам по себе не является доказательством улучшения.
- Для заявления об ускорении без потери качества требуются парные совпадения структур и допуски коэффициентов на численно сложных случаях, не только время выполнения.

## 5. S3: переносимость и смена режима

Системы и траектории S3 должны оставаться полностью вне S0/S1/S2 настройки. Проверяются: новые начальные условия, различная длина траектории, неоднородные сетки, коррелированные производные, и отдельно — режим с шумом (только в случае согласования научной постановки). При нарушении идентифицируемости следует фиксировать неопределённый результат, а не ошибочно считать проблему решённой регуляризацией.

Проверку коэффициентной нестабильности на нескольких начальных условиях необходимо отличать от случайного разбиения **той же** траектории на соседние окна — последнее не является независимым внешним экспериментом.
